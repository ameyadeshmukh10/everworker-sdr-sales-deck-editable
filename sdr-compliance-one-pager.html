EverWorker

AI SDR — Data Compliance & Security

The AI SDR is an autonomous prospecting worker built around data minimization: it stores only the contact fields needed to deliver outreach, writes campaign content exclusively from publicly available information, and runs as a fully isolated single-tenant deployment per client.

Only outreach-essential fields stored
Content from public sources only
Private LLM endpoints — never used for training
Single-tenant, fully isolated deployments
Opt-outs enforced automatically & auditably

1 Data minimization — what is stored

All contact records originate from the client's own CRM (inbound) or B2B enrichment providers (outbound). The CRM remains the system of record throughout.

FieldWhy it's needed
Full nameAddressing the recipient
Business emailEmail delivery
Job title / positionPersona-appropriate messaging
Company & domainAccount research (public sources)
LinkedIn profile URLLinkedIn outreach delivery
CountryEmail scheduling
Marketing fieldsTouchpoint context (e.g. whitepaper download, webinar registration)

Never collected or stored: phone numbers, home or personal addresses, personal (non-business) email accounts, or sensitive / special-category personal data of any kind.

2 Campaign content — public sources only

  • Account level: company news, the public website, public DNS records, posted job openings.
  • Client-provided: approved messaging & positioning, case studies, publicly shared marketing materials.
  • Contact level: inferences from job title; LinkedIn data only where the profile is public; statements publicly attributable to the contact.

Third-party enrichment for company signals receives the company domain only — personal data is never sent to enrichment providers.

3 LLM usage — private endpoints, no training

  • Private per-client endpoint with dedicated credentials; prompts and outputs are never shared across clients.
  • Submitted data is not used to train models, per the commercial API terms in effect.
  • Transient processing: minimal fields + public research in, drafted copy out — stored only inside the client's deployment.
  • EverWorker manages endpoint procurement, security, billing, and operation — no access to your LLMs required.

4 Deployment — single tenant, isolated data

  • Dedicated stack per client on Railway: own application service, databases, and storage volume — no shared layer between clients.
  • Private networking: databases are reachable only over the project's private network, never exposed publicly.
  • Per-client credentials everywhere: every integration (CRM, sending platforms, LLM API) uses isolated keys scoped to that client.
  • No cross-client data plane: no shared pipeline, queue, or analytics store — leakage is impossible by construction.
  • EverWorker manages the entire infrastructure layer — no access to your email accounts or sequencing tools required.

5 Access & security controls

  • TLS/HTTPS on all traffic to third-party APIs and between services.
  • Operations console behind authenticated login: salted password hashes, signed session tokens.
  • Inbound webhooks authenticated with a shared secret; rejected without it.
  • API secrets live in platform service configuration — never in source code or repositories.
  • CRM access via a scoped private-app token (least privilege), set up during onboarding.
  • The web console reads the pipeline database read-only; writes go through controlled pipeline jobs only.

6 Opt-out & suppression

Do-not-contact status is enforced automatically and continuously. Contacts can opt out via links or written replies on email or LinkedIn; any contact flagged in the client's CRM (opted out, booked a meeting, became an opportunity) is excluded at every stage.

Flag raisedopt-out or CRM status →Dropped at CRM pull →Re-checked at enrollment →30-min sweepstops in-flight, all channels →Audit ledger + CRM timeline

Suppression is one-way: a stopped sequence for an opted-out contact stays stopped and can never resume for that contact.
